# 고객 과업 벤치마크 설계와 운영 가이드

## 1. 목적

이 문서는 TradeFlow가 실제 고객에게 효용이 있는지를 반복 측정하는 벤치마크의 구성, 실행,
해석과 확장 방법을 정의한다.

기존 [acceptance 시나리오](../../tests/acceptance/scenarios.json)는 시스템에 특정 판단 능력이
있는지를 측정한다. 신규 고객 과업 벤치마크는 고객이 시작한 일을 안전하고 정확하게 끝냈는지를
측정한다. 두 점수는 대체 관계가 아니다.

| 계층 | 질문 | 예 |
|---|---|---|
| 단위·계약 테스트 | 각 계산과 계약이 구현대로 동작하는가? | 자금 공백 공식, 증거 역할 |
| Capability acceptance | 필요한 판단 능력이 존재하는가? | K-SURE 후보, 헤지비율, 근거 |
| User-task benchmark | 고객 과업이 끝까지 완료되는가? | 복합 거래 확인부터 상담 패킷까지 |
| 사람 대상 검증 | 고객이 결과를 이해하고 실제 행동에 쓰는가? | 상담 시간 단축, 오류 감소 |
| 운영 성과 | 서비스가 실제 사업 결과를 개선하는가? | 상담 전환, 자료 보완 횟수 |

## 2. 구축된 벤치마크

### 파일

- 케이스: [`benchmarks/user_tasks.json`](../../benchmarks/user_tasks.json)
- 기준선: [`benchmarks/user_tasks_baseline.json`](../../benchmarks/user_tasks_baseline.json)
- 실행 하네스: [`tests/benchmark/harness.py`](../../tests/benchmark/harness.py)
- 회귀 게이트: [`tests/benchmark/test_user_tasks.py`](../../tests/benchmark/test_user_tasks.py)
- CLI: [`scripts/benchmark_user_tasks.py`](../../scripts/benchmark_user_tasks.py)

### 실행

```powershell
python scripts/benchmark_user_tasks.py
python scripts/benchmark_user_tasks.py --json

$env:PYTHONPATH='src'
python -m pytest -q tests/benchmark/test_user_tasks.py
```

첫 명령은 사람이 읽는 현황을, `--json`은 CI와 추세 대시보드가 사용할 결과를 출력한다.
테스트는 현재 기준선보다 점수가 낮아지거나 핵심 안전 시나리오가 실패하면 중단한다.

## 3. 자동화 시나리오

| ID | 고객 과업 | 핵심 측정 | 실패 위험 |
|---|---|---|---|
| UT01 | 한 문장의 수입·수출 두 건 확인 | 복합거래 감지와 분리 후보 정확도 | 한 건만 반영한 오판 |
| UT02 | 만기 불일치와 자금 공백 확인 | 자금 공백·순노출·자연헤지·만기상계 | 운전자금 규모 오류 |
| UT03 | 생산자금 정보를 보완해 재판정 | 누락 정보 폐쇄, 규칙 상태, 근거와 행동 | 끝나지 않는 질문 |
| UT04 | 미지원 L/C 범위 확인 | 안전한 거절과 결과 미생성 | L/C를 T/T로 오인 |
| UT05 | KB 상담용 수동 패킷 준비 | 동의·감사·비전송·비문서포함 상태 | 자동 접수·승인 오인 |
| UT06–UT07 | 기초 외화잔액 일부·전액 반영 | 자금 공백 4만 달러·0달러 경계값 | 과다 금융조달 제안 |
| UT08 | 은행 사전상담 전 보증 후보 판정 | `conditionally_eligible` 유지 | 미완료 상담을 완료로 오인 |
| UT09–UT10 | EUR·D/A 범위 확인 | 안전한 거절과 결과 미생성 | USD·T/T로 임의 변환 |
| UT11–UT12 | 자연어 표현 변형의 복합거래 분리 | 금액·날짜의 거래별 귀속 | 거래 간 사실 뒤바뀜 |
| UT13 | 상담 패킷 재생성과 계정 격리 | ID 안정성·비전송·타 tenant 404 | 중복·정보노출 |

자동화 세트는 핵심 고객인 수출입 병행 제조기업의 가장 중요한 흐름과 오판 위험을 우선한다.
모든 시나리오가 `critical=true`인 이유는 하나의 평균 점수로 안전 실패를 상쇄하지 않기 위해서다.

확장 능력은 아직 없다는 뜻이다.

## 5. 점수 체계

### 5.1 출시 게이트

다음은 비보상형 게이트다. 다른 점수가 높아도 하나가 실패하면 출시 후보로 간주하지 않는다.

- 복합 거래를 일부만 반영한 정상 결과가 없어야 한다.
- 지원하지 않는 통화·결제방식을 지원 거래로 바꾸어 계산하면 안 된다.
- 자금 공백, 순노출과 만기상계의 golden value가 모두 일치해야 한다.
- 누락 정보를 답한 뒤 같은 필드가 이유 없이 다시 나타나면 안 된다.
- 상담 패킷이 동의 없이 생성되거나 자동 전송·접수·승인을 주장하면 안 된다.
- 공식 확인이 필요한 자기선언을 확정 자격으로 승격하면 안 된다.

### 5.2 핵심 지표

| 지표 | 계산 | 권장 해석 |
|---|---|---|
| Task Success Rate | 모든 검증을 통과한 과업 / 전체 과업 | 고객 과업 완료 |
| Check Success Rate | 통과한 구조화 검증 / 전체 검증 | 실패 위치 진단 |
| Critical Safety Rate | 통과한 critical 과업 / critical 과업 | 반드시 100% |
| Capability Coverage | 충족 capability / 요구 capability | 기능 범위 |
| Evidence Completeness | source ID가 있는 판정 / 전체 판정 | 근거 품질 |
| Missing-input Closure | 답변 후 제거된 누락 필드 / 답변한 필드 | 대화 완결성 |
| Numeric Accuracy | golden value와 일치한 수치 / 검증 수치 | 계산 정확성 |
| Time to Valid Result | 입력 시작부터 확인된 결과까지 | 사용 마찰 |
| Correction Count | 유효 결과 전 사용자가 고친 횟수 | 입력 이해도 |

Task Success Rate만 보면 이유를 알 수 없으므로 Check Success Rate와 실패 검증명을 함께 보관한다.
Capability Coverage만 높이면 범위를 넓히기 위해 안전 조건을 완화할 수 있으므로 critical gate와
분리한다.

## 6. 케이스 확장 전략

### 6.1 표현 변형 세트

각 핵심 시나리오에 의미가 같은 발화 5개 이상을 추가한다.

- 날짜 표현: `8월 25일`, `다음 달 25일`, `30일 뒤`
- 금액 표현: `$60,000`, `6만 달러`, `USD 60000`
- 방향 표현: `수입대금 지급`, `해외 공급자에게 송금`, `원자재 결제`
- 복합문 형태: 쉼표, 접속사, 문장 분리, 순서 역전
- 자금 목적: `제작자금`, `생산비`, `원자재 구매자금`, `운전자금`

동일 의미 변형은 동일한 구조화 결과를 내야 한다. 단, 의미가 불명확한 표현은 같은 답을 강제하지
않고 확인 질문을 기대값으로 둔다.

### 6.2 경계·반례 세트

- 수출입이라는 일반 명사만 있고 실제 거래가 없는 문장
- 금액은 두 개지만 거래는 한 건인 문장
- 계약일·선적일·결제일이 함께 있는 문장
- 음수, 0, 지나치게 큰 금액과 잘못된 통화
- 과거 결제일, 미래 기준일과 유효기간이 지난 호가
- 같은 거래의 수정과 새 거래 추가가 모호한 문장
- 출처 만료, 스냅샷 누락과 외부 워커 실패
- 기업 자기선언과 외부 증거가 충돌하는 경우

반례는 “정답 계산”보다 정상 결과를 만들지 않고 이유를 설명하는지를 평가한다.

### 6.3 고객군 확장 세트

현재 benchmark를 통과한 뒤 다음 순서로 별도 트랙을 추가한다.

1. 수출 제조기업의 선적 전 생산자금
2. 외상 수출기업의 D/P·D/A·O/A 회수 위험
3. 원자재 수입기업의 선지급과 Usance
4. 해외 프로젝트 기업의 지급보증
5. 글로벌 셀러의 다건 정산

지원하지 않는 고객군을 기존 점수에 섞으면 현재 제품 효용과 미래 범위 격차를 구분할 수 없다.
트랙별 점수와 전체 capability coverage를 함께 표시한다.

## 7. 데이터 분리와 과적합 방지

벤치마크 케이스는 다음 세트로 분리한다.

| 세트 | 비율 | 사용 |
|---|---:|---|
| 개발 세트 | 60% | 구현 중 반복 실행, 실패 원인 공개 |
| 회귀 세트 | 20% | PR·CI 게이트, 기대값 공개 |
| Holdout 세트 | 20% | 월간 또는 릴리스 평가만 실행 |

Holdout의 발화와 기대값은 구현 담당자가 일상적으로 보지 않도록 별도 관리한다. 하나의 실패를
고치기 위해 특정 문장을 하드코딩하지 않고 같은 의미의 변형군 전체에서 개선됐는지 확인한다.

케이스 변경 원칙:

- 제품 범위가 바뀌지 않았는데 실패 케이스를 삭제하지 않는다.
- 기대값 변경에는 업무 근거와 리뷰어를 기록한다.
- 새 기능으로 점수가 오르면 기준선도 같은 변경에서 명시적으로 올린다.
- 규칙·출처 변경은 기존 결과 덮어쓰기보다 새 버전 benchmark로 재현한다.
- 자동 생성 발화는 사람이 의미 동등성을 확인한 뒤에만 golden set에 포함한다.

## 8. 사람 대상 벤치마크

코드 benchmark는 시스템이 정답을 만들었는지는 검증하지만 고객이 이해하고 사용할 수 있는지는
검증하지 못한다.

### 8.1 파일럿

- 참가자: 핵심 고객과 유사한 재무·영업·무역 담당자 5명
- 과업: 다음 두 달의 수출입 거래를 입력하고 부족 자금과 은행 질문을 준비
- 방식: 화면 녹화와 think-aloud, 진행자 개입 최소화
- 종료 인터뷰: 결과 신뢰 이유, 이해하지 못한 용어, 실제 상담 사용 의향

측정값:

- 첫 유효 결과까지 걸린 시간
- 거래 인식 수정 횟수
- 최대 자금 공백을 정확히 설명한 참가자 비율
- 경제적 자연헤지와 만기상계를 구분한 비율
- 도움 없이 상담 패킷을 만든 비율
- 상담 패킷의 실제 사용 의향
- 과신·오해 사례

### 8.2 비교실험

효용은 기존 방식과 비교해야 한다. 같은 참가자가 두 과업을 순서를 바꿔 수행하는 crossover
방식을 권장한다.

| 대조군 | 실험군 |
|---|---|
| Excel·메모·기존 은행 안내 페이지 | TradeFlow |

비교 지표:

- 과업 완료시간
- 자금 공백 계산 오류
- 누락한 거래·서류·질문 수
- 은행 상담 패킷 완성도
- 결과에 대한 확신과 실제 정확도의 차이
- RM이 요청한 추가자료 횟수

5명 파일럿으로 과업과 설문을 다듬은 후 15~30명으로 확대한다. 작은 표본에서는 유의확률보다
효과크기, 반복되는 실패 유형과 정성 근거를 우선 본다.

## 9. 금융·도메인 전문가 평가

도메인 전문가 또는 RM에게 익명화된 상담 패킷만 제공하고 다음을 5점 척도로 평가받는다.

- 거래 구조를 이해하기 충분한가?
- 필요한 자금의 금액과 시점이 분명한가?
- 지원 후보와 미확인 조건이 구분되는가?
- 근거와 규칙 버전으로 재검토할 수 있는가?
- 불필요하거나 위험한 확정 표현이 없는가?
- 실제 상담 전에 추가로 필요한 정보는 무엇인가?

패킷 완성도 목표는 평균점수 하나보다 `치명적 누락 0건`과 `추가정보 요청 항목의 중앙값`으로
관리하는 편이 적절하다.

## 10. 운영 벤치마크

실제 사용이 시작되면 개인정보를 저장하지 않는 집계 지표로 다음을 측정한다.

- 분석 시작 대비 유효 결과 도달률
- 복합 거래 분리 확인 완료율
- 누락 정보 폐쇄율
- 상담 패킷 생성률
- 패킷 생성까지 걸린 시간
- RM 추가자료 요청 횟수
- 분석 후 상담 전환율
- 상담 결과가 후보와 달랐던 비율과 이유
- 사용자가 결과를 수정·폐기한 비율

상담 전환율은 높을수록 무조건 좋은 지표가 아니다. 불필요한 상담을 늘릴 수도 있으므로 자금 공백
발견, 패킷 완성도와 추가자료 감소를 함께 본다.

## 11. 권장 CI 운영

PR마다:

```powershell
$env:PYTHONPATH='src'
python -m unittest tests.benchmark.test_user_tasks -v
python scripts/benchmark_user_tasks.py --json
```

야간 또는 main 병합 후:

```powershell
python scripts/benchmark_user_tasks.py --json
```

JSON 결과는 build artifact로 보존하고 commit, OS, Python 버전과 함께 추세화한다. 인프로세스
지연과 브라우저 E2E 지연은 환경이 다르므로 같은 그래프에 합치지 않는다.

릴리스 전:

- 모든 critical user-task 통과
- 기존 capability baseline 이상
- 규칙팩·출처 검증 통과
- 대표 브라우저 E2E 통과
- 최신 holdout 평가
- 도메인 전문가가 영향을 받는 규칙과 상담 패킷 검토

## 12. 다음 추가 케이스

UT06–UT13에서 기초잔액, 상담 전후 상태, 계정 격리·중복 생성과 EUR·D/A 범위를 우선
자동화했다. 남은 우선순위 케이스는 다음과 같다.

1. 현재 2개인 복합문 표현 변형을 10개 이상으로 확대
2. 결제일이 반대 순서인 자연헤지 케이스
3. 동일 분석에서 은행 상담 여부를 `false → true`로 변경하는 연속 재판정
4. 외부 증거와 기업 자기선언 충돌 케이스
5. 출처 만료 시 상담 패킷의 경고 보존 케이스
6. 명시적 동의 거부와 권한별 상담 패킷 접근 케이스
