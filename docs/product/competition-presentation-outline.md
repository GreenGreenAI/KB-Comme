# TradeFlow 대회 제안서 장별 원고·구성안

## 1. 문서 목적

이 문서는 PPT를 만들기 전, 심사위원에게 전달할 이야기와 각 장의 화면 문구를 확정하기 위한
콘텐츠 명세다. 제안서의 중심 문장은 다음과 같다.

> **TradeFlow는 무역계약의 조건을 현금흐름과 위험 시나리오로 변환하고, 조건 변화가
> 자금·환위험·보험·금융조치에 미치는 연쇄 영향을 보여주는 Trade Deal Decision Twin이다.**

발표의 목표는 심사위원이 다음 세 가지를 분명히 이해하게 하는 것이다.

1. 환리스크·서류심사·뉴스 분석만으로는 실제 거래 의사결정이 완결되지 않는다.
2. TradeFlow의 핵심 가치는 분리된 계약·현금흐름·위험·금융조치를
   `Clause-to-Cash-to-Action`으로 연결하는 데 있다.
3. 현재 구현된 기반과 앞으로 구현할 Decision Twin 기능은 명확히 구분돼 있다.

---

## 2. 전체 구성

| 장 | 역할 | 심사위원이 가져가야 할 한 문장 |
|---:|---|---|
| 1 | 표지 | TradeFlow는 Trade Deal Decision Twin이다. |
| 2 | 구체적 문제 | 계약조건이 결제일을 만들고, 결제일이 자금 공백과 환노출 기간을 만든다. |
| 3 | 문제 확장 | 환노출 감소와 결제일 유동성 확보는 서로 다른 결정이다. |
| 4 | 업무 단절 | 계약·현금흐름·환위험·보험·금융상담이 서로 다른 업무로 분리돼 있다. |
| 5 | 통합 가치 | TradeFlow는 흩어진 판단을 하나의 거래 맥락으로 연결한다. |
| 6 | 해결 구조 | Clause를 Cash로 바꾸고, 위험 변화에서 Action까지 연결한다. |
| 7 | 현재 맥락 인식 | 고객·문서·시스템 사실을 출처와 상태가 있는 거래 맥락으로 만든다. |
| 8 | 목표 시나리오 | 결제조건 변경을 하나의 거래 시뮬레이션으로 재계산한다. |
| 9 | Decision Delta | 조건 하나가 여러 위험과 금융 필요기간을 어떻게 바꾸는지 보여준다. |
| 10 | 실행 대안 | 결과를 재협상·보험·금융·부분헤지 선택으로 연결한다. |
| 11 | Decision Passport | 결정 근거와 미확인 조건을 상담 가능한 패킷으로 남긴다. |
| 12 | 기술·안전 구조 | LLM은 설명하고 결정론적 엔진은 금액과 상태를 책임진다. |
| 13 | 구현 경계 | 기반 기능은 구현됐지만 완전한 Decision Twin은 아직 목표 상태다. |
| 14 | 검증·로드맵 | 검증된 기반 위에 조항 구조화·연쇄 전파·실행 대안을 순서대로 확장한다. |
| 15 | 결론 | 환리스크 도구를 넘어 거래 단위 의사결정 인프라로 간다. |

## 3. 장별 원고와 화면 구성

### 1장. 표지 — 서비스의 정체성을 먼저 고정한다

**화면 제목**

> TradeFlow

**화면 부제**

> Trade Deal Decision Twin

**설명 문구**

> 계약조건을 현금흐름과 위험 시나리오로 변환하고,  
> 금융조치의 연쇄 변화까지 연결합니다.

**하단 태그라인**

> Clause-to-Cash-to-Action

**구성**

- 좌측 정렬의 미니멀 표지로 구성한다.
- 서비스명, 새로운 카테고리명, 한 문장 설명의 3단 위계를 사용한다.
- 기능 목록이나 검증 수치는 표지에 넣지 않는다.

**발표 포인트**

“저희는 환율 전망이나 상품 추천을 하나 더 만드는 팀이 아닙니다. 계약조건의 변화가 거래의
현금흐름과 위험, 금융조치에 어떻게 이어지는지를 보여주는 거래 단위 의사결정 AI입니다.”

---

### 2장. 문제 — 계약조건이 자금 공백과 위험을 만든다

**화면 제목**

> 계약서의 결제조건이 60일간 USD 60,000의 자금 공백을 만듭니다

**화면 본문**

```text
계약조건

수입계약                           수출계약
2026.08.25 T/T 지급               선적 후 60일 결제
- USD 60,000                      + USD 100,000

                 ↓ 현금흐름 이벤트로 변환

2026.08.25                         2026.10.24
- USD 60,000                      + USD 100,000
수입대금 지급                      수출대금 수취

자금 공백       USD 60,000
공백 기간       60일
환노출 기간     60일
```

**하단 결론**

> 계약조건은 문서 속 문장이 아니라 자금과 위험을 결정하는 변수입니다.

**구성**

- 화면 상단에는 두 계약의 결제조건을 좌우로 배치한다.
- 중앙의 아래쪽 화살표로 계약조건이 실제 지급·수취 이벤트로 변환되는 과정을 보여준다.
- 날짜 축에서는 두 결제일 사이를 붉은 선으로 연결해 60일 자금 공백을 강조한다.
- 하단에는 자금 공백 금액, 공백 기간과 환노출 기간을 동일한 위계로 제시한다.

**발표 포인트**

“기업 전체로는 4만 달러가 남지만, 수입계약의 지급일과 수출계약의 ‘선적 후 60일’ 조건 때문에
수출대금을 받기 전 60일 동안 6만 달러가 부족합니다. TradeFlow는 계약서의 조건을 실제
현금흐름 이벤트로 변환해 자금 공백과 환노출 기간을 계산합니다.”

**다음 장 연결 질문**

> 그렇다면 ‘선적 후 60일 결제’가 ‘90일 결제’로 바뀌면 무엇이 함께 달라질까요?

**표시 상태**

- 현재 구현: 확정된 결제일을 기반으로 자금 공백·공백 기간·환노출 계산
- 목표 기능: 문서의 `선적 후 60일` 같은 상대일 결제조건을 자동 추출해 결제일로 변환

---

### 3장. 문제 확장 — 환위험만 보면 절반을 놓친다

**화면 제목**

> 환위험만 보면 자금 문제의 절반을 놓칩니다

**좌측 문구**

```text
경제적 자연헤지
USD 60,000
전체 수출·수입 금액에서 서로 상계 가능한 규모
```

**우측 문구**

```text
결제시점 상계
USD 0
수입 지급일에 실제로 사용할 수 있는 수출대금
```

**하단 결론**

> 환노출 감소와 결제일 자금 확보는 서로 다른 의사결정입니다.

**구성**

- 화면을 정확히 좌우 2분할한다.
- 같은 거래가 경제적 관점과 결제일 관점에서 다르게 보인다는 대비를 만든다.
- 숫자는 크게, 설명은 두 줄 이내로 제한한다.

**표시 상태:** 현재 엔진에서 직접 계산 가능

---

### 4장. 업무 단절 — 한 거래의 판단 근거가 여러 업무에 흩어져 있다

**화면 제목**

> 한 거래의 판단 근거는 다섯 개의 업무에 흩어져 있습니다

**화면 중심 분류**

```text
계약·서류       현금흐름       환위험         신용·보험       금융상담
결제조건·일정   지급·수취      노출·헤지      국가·바이어     금액·기간·서류
```

**하단 결론**

> 각각의 분석 결과는 있지만, 하나의 거래 결정으로 연결되지 않습니다.

**구성**

- 동일한 거래가 계약 검토, 자금 계산, 환위험 관리, 보험 확인과 금융상담으로 분리되는 모습을
  좌우 흐름으로 보여준다.
- 각 업무 사이의 연결선을 중간에서 끊어, 정보가 다음 판단으로 이어지지 않는 문제를 표현한다.
- 화면과 발표 원고는 고객의 업무 흐름과 단절 문제에만 집중한다.

**발표 포인트**

“수출입기업은 하나의 거래를 판단하기 위해 계약서를 보고, 현금흐름을 다시 계산하고,
환위험과 바이어 신용을 확인한 뒤 금융기관에 가져갈 자료를 또 정리합니다. 문제는 기능이 없는
것이 아니라, 같은 거래에 대한 판단 근거가 서로 연결되지 않는다는 점입니다.”

---

### 5장. 통합 가치 — 흩어진 판단을 하나의 거래 맥락으로 연결한다

**화면 제목**

> TradeFlow는 흩어진 판단을 하나의 거래 맥락으로 연결합니다

**중앙 핵심 문장**

> 계약조건 → 현금흐름 → 위험 변화 → 실행 대안  
> 하나의 조건이 바뀌면 전체 판단을 같은 거래 안에서 다시 계산합니다.

**하단 명칭**

> Trade Deal Decision Twin

**구성**

- 이 장은 4장에서 끊겨 있던 다섯 업무를 하나의 선으로 연결하는 모습으로 구성한다.
- `계약조건`, `현금흐름`, `위험 변화`, `실행 대안`의 네 단계를 차례로 보여준다.
- 중앙의 `하나의 거래 맥락`과 하단의 `Trade Deal Decision Twin`을 노란색으로 강조한다.

**발표 포인트**

“TradeFlow는 별도 분석 결과를 한 화면에 모으는 서비스가 아닙니다. 계약조건이 실제 지급과
수취 일정을 어떻게 만들고, 그 일정이 자금과 위험을 어떻게 바꾸며, 어떤 대응이 필요한지를
하나의 거래 맥락 안에서 연결합니다.”

---

### 6장. 해결 구조 — Clause-to-Cash-to-Action

**화면 제목**

> TradeFlow는 Clause-to-Cash-to-Action을 연결합니다

**5단계 문구**

```text
01 계약 조건       금액·통화·선적일·결제조건
02 현금 변환       날짜별 지급·수취 이벤트
03 위험 전파       자금 공백·환노출·보험·금융기간
04 대안 비교       재협상·보험·채권금융·운전자금·부분헤지
05 결정 인계       Decision Delta·Decision Passport
```

**하단 결론**

> 분석 리포트가 아니라 행동 가능한 결정 상태까지

**구성**

- 좌에서 우로 이어지는 단일 흐름으로 구성한다.
- 3단계 `위험 전파`를 노란색으로 강조한다.
- 박스 안에는 명사형 문구만 넣고 자세한 설명은 발표로 처리한다.

**표시 상태**

- 현재 구현: 거래 사실, 날짜별 현금 이벤트, 자금 공백·환노출, Delta·Passport
- 목표 기능: 계약 조항 자동 구조화, 위험 연쇄 전파, 실행 대안 통합 비교

---

### 7장. 맥락 인식 — 사실을 추측하지 않고 연결한다

**화면 제목**

> 고객의 현재 상황을 출처와 상태가 있는 거래 맥락으로 만듭니다

**화면 왼쪽: 입력 사실**

```text
사용자 확인
- 보유 외화
- 위험 허용한도
- 실제 결제 관행

문서 확인
- 금액·통화
- 선적일·결제일
- 거래 당사자
```

**화면 오른쪽: 정보 보완 경로**

```text
고객에게 질문       결과를 바꾸는 정보
시스템에서 조회     시장·실적·정책 정보
전문가가 확인       자격·규정·승인 조건
```

**하단 결론**

> 맥락 인식은 AI의 추측이 아니라, 확인된 사실의 연결입니다.

**구성**

- 좌측은 현재 확보한 사실, 우측은 부족한 정보의 주체로 나눈다.
- 확인 상태를 `confirmed`, `insufficient`, `expert review` 색상으로 구분한다.

**표시 상태:** 현재 구조의 핵심 기능

---

### 8장. 목표 데모 — 결제조건 하나를 바꿔 거래를 다시 본다

**화면 제목**

> “선적 후 60일 결제”가 “90일 결제”로 바뀐다면?

**화면 왼쪽: 기준 조건**

```text
기준 시나리오
수취일             D+60
자금 공백 기간      60일
환노출 기간         60일
금융 필요기간       60일
```

**화면 오른쪽: 변경 조건**

```text
변경 시나리오
수취일             D+90
자금 공백 기간      90일
환노출 기간         90일
금융 필요기간       90일 검토
추가 확인           바이어 신용·보험 가능 여부
```

**구성**

- 전후 2분할 비교로 구성한다.
- 바뀐 값만 붉은색으로 표시한다.
- 하단에 `목표 데모` 배지를 두어 현재 완성 기능으로 오해하지 않게 한다.

**표시 상태:** 목표 기능. 현재는 사용자가 결제일을 직접 변경해 재분석할 수 있으나,
상대일 조항 추출과 30·60·90일 시나리오 자동 생성은 미구현이다.

---

### 9장. Decision Delta — 연쇄 변화를 한 화면에서 증명한다

**화면 제목**

> 조건 변경 전후에 바뀐 것만 보여줍니다

**화면 중심**

```text
결제조건           D+60  →  D+90
자금 공백 기간      60일  →  90일
환노출 기간         60일  →  90일
금융 필요기간       60일  →  90일 검토
보험·신용 확인      선택  →  우선 확인
```

**하단 문구**

> 금액이 같아도 기간과 필요한 행동은 달라집니다.

**구성**

- 전체 분석 결과를 반복하지 않고 변경된 항목만 세로로 정렬한다.
- 좌측은 Before, 우측은 After, 중앙은 화살표로 구성한다.
- 금융기관 상담 전에 확인해야 할 다음 질문을 우측 하단에 둔다.

**표시 상태**

- 현재 구현: 자금 공백·순노출·자연헤지·후보 상태·행동·서류의 Delta
- 목표 기능: 공백 기간·환노출 기간·보험·금융기간의 자동 연쇄 Delta

### 10장. Action — 숫자를 대응 선택지로 바꾼다

**화면 제목**

> 같은 위험에도 대응 방법은 하나가 아닙니다

**화면 비교 항목**

| 대안 | 해결하는 문제 | 비교할 근거 | 주요 전제조건 |
|---|---|---|---|
| 결제조건 재협상 | 공백 기간 단축 | 수취일·협상 가능성 | 바이어 동의 |
| 수출채권 조기 현금화 | 수출대금 선회수 | 조달비용·소구 여부 | 채권·바이어 적격성 |
| 운전자금 | 지급일 유동성 확보 | 필요금액·기간·금리 | 한도·담보·심사 |
| 수출보험 | 미수·신용위험 완화 | 보상범위·면책·보험료 | 국가·바이어·거래 적격성 |
| 부분헤지 | 잔여 환노출 제한 | 헤지비율·만기·비용 | 실제 노출·내부 한도 |

**하단 결론**

> 상품 추천이 아니라, 현재 거래에 필요한 조치의 목적·비용·조건을 비교합니다.

**구성**

- 실제 화면에는 표 전체를 넣지 않고 3개 대표 대안만 보여준다.
- 발표 상황에서는 `재협상`, `채권금융/운전자금`, `부분헤지·보험`의 세 갈래로 묶는다.
- 비용 숫자가 확인되지 않은 항목은 임의로 생성하지 않고 `조회 필요`로 표시한다.

**표시 상태:** 일부 구성요소 구현, 통합 대안 비교는 목표 기능

### 11장. Decision Passport — 결정 근거를 상담자료로 보존한다

**화면 제목**

> 금융기관이 검토할 수 있는 최소 결정 패킷으로 남깁니다

**화면 본문**

```text
사실      거래·문서에서 확인한 값과 확인 주체
계산      자금 공백·순노출·자연헤지·시나리오 결과
규칙      rule ID·version·검토 상태
출처      공식 URL·기준일·content hash
변화      Decision Delta
미확인    추가 질문·필요서류·전문가 확인 항목
권한      자동 승인 아님·은행 최종 검증 필요
```

**구성**

- 왼쪽은 Passport 문서, 오른쪽은 `상담 준비 완료`의 의미를 설명한다.
- `자동 승인 아님`을 별도 회색 박스로 표시한다.
- 다운로드·수동 전달과 향후 KB Adapter 연계를 하단에서 구분한다.

**표시 상태:** 현재 구현

### 12장. 기술·안전 구조 — 생성형 AI와 금융 판단을 분리한다

**화면 제목**

> LLM은 설명하고, 엔진은 금액과 상태를 책임집니다

**4단계 문구**

```text
01 확인된 사실       사용자 입력·문서 확인
02 결정론적 코어     현금흐름·환노출·규칙 판정
03 Decision Packet  숫자·상태·출처·버전
04 표현·검토         LLM 설명·사람의 승인
```

**하단 결론**

> 같은 입력과 같은 규칙 버전이면 같은 결정 패킷을 재현합니다.

**구성**

- 4개 단계를 수평으로 연결한다.
- 3단계 Decision Packet을 노란색으로 강조한다.
- LLM이 계산이나 자격 판정을 직접 생성하지 않는다는 경계를 명확히 한다.

**표시 상태:** 현재 구현 원칙

### 13장. 구현 경계 — 현재 가능한 것과 목표를 분리한다

**화면 제목**

> 기반은 구현됐지만, 완전한 Decision Twin은 아직 목표 상태입니다

**좌측: 현재 구현**

```text
✓ 거래·복합 거래 intake
✓ 문서 업로드·추출·사용자 확인·불일치 검사
✓ 자금 공백·순노출·자연헤지·만기상계
✓ FX 시나리오·헤지비율 계산
✓ Next Decisive Question
✓ Decision Delta·Decision Passport
✓ 수동 상담 lifecycle
```

**우측: 목표 기능**

```text
△ Incoterms·상대일 결제조건 자동 추출
△ 확정 문서 사실의 거래 원장 자동 반영
△ 30·60·90일 지연 시나리오 자동 생성
△ 지연→공백→환노출→보험·금융기간 연쇄 재계산
△ 재협상·보험·채권금융·운전자금·부분헤지 통합 비교
△ 실제 buyer·country·news·KB 데이터 연계
```

**구성**

- 녹색 `현재 구현`과 노란색 `목표 기능`의 2열 구조를 사용한다.
- 목표 기능을 흐리게 숨기지 말고 제품 확장 로드맵으로 제시한다.
- `미구현`을 실패가 아니라 대회 이후 확장계획으로 포장하되 현재 기능처럼 표현하지 않는다.

## 4. 작성 원칙

### 4.1 화면 문구 원칙

- 한 장에는 하나의 주장만 둔다.
- 제목은 주제가 아니라 결론형 문장으로 작성한다.
- 본문은 발표자가 읽을 대본이 아니라, 심사위원이 3초 안에 구조를 이해할 단서만 둔다.
- 현재 기능에는 `현재 구현`, 미완성 확장 기능에는 `목표 기능` 또는 `목표 데모`를 표시한다.
- 확인되지 않은 금리·보험료·상품 자격을 임의로 쓰지 않는다.

### 4.2 시각 구성 원칙

- 기존 제안서의 흰 배경, 검정·회색 본문, 노란색 강조 체계를 유지한다.
- 표보다 전후 비교, 시간축, 단일 흐름을 우선 사용한다.
- 노란색은 핵심 단계 또는 목표 상태 한 곳에만 사용한다.
- 실제 제품 화면이 없는 경우 가짜 UI를 만들지 않고, 구조화된 데이터와 변화값을 시각화한다.

### 4.3 발표 순서의 논리

```text
실제 고객 문제
→ 환리스크만으로 부족한 이유
→ 분절된 업무와 정보
→ 하나의 거래 맥락
→ Clause-to-Cash-to-Action 작동 방식
→ 목표 사용 시나리오와 Decision Delta
→ 실행 대안과 상담 인계
→ 기술 안전성
→ 현재 구현과 목표 기능의 경계
→ 검증과 로드맵
```

이 순서를 유지하면 환리스크 기능을 보유하면서도, 발표의 중심은 `거래조건 변화의 연쇄 영향과
실행 의사결정`으로 이동한다.
