# 고객층 조사 기반 서비스 및 KB 연계 준비도 리뷰

## 1. 목적

이 문서는 [KB금융그룹 수출입금융 조직 및 서비스 조사](../research/kb-export-import-finance.md)에
추가된 고객층, 이용 목적, 실제 절차와 대표 시나리오를 기준으로 TradeFlow의 현재 제품 방향과
구현 범위를 다시 검토한다.

검토 질문은 다음과 같다.

1. 조사된 고객 문제와 TradeFlow가 현재 해결하는 문제가 일치하는가?
2. 어떤 고객군을 초기 핵심 고객으로 두어야 하는가?
3. 현재 구현은 고객이 은행 상담 전에 의사결정을 준비하는 데 충분한가?
4. KB의 비공개 데이터나 API를 사용할 수 없는 상태에서 어떤 확장 경계를 남겨야 하는가?

이 리뷰는 KB국민은행과의 제휴, 상품 판매, 대출 승인 또는 기업뱅킹 연동이 이미 가능하다고
가정하지 않는다.

## 2. 검토 기준

고객층 조사에서 확인한 핵심 고객은 반복적인 수출입 거래가 있으나 담보, 현금흐름 또는 무역
전문인력이 충분하지 않은 중소·중견 제조·무역기업이다. 이들이 서비스를 이용하는 주요 이유는
다음 다섯 가지다.

- 생산·수입대금 지급과 수출·판매대금 회수 사이의 현금 공백 해소
- 외상 수출대금의 미회수 위험 관리
- 계약과 결제 사이의 환율변동으로부터 거래마진 보호
- 해외 입찰·계약에 필요한 보증과 신용 보강
- 통관, 관세, FTA, 거래처 조사와 외국환 신고 전문성 보완

KB의 실제 업무는 단일 상품 조회보다 `거래구조 상담 → 신용평가·한도약정 → 거래별 신청 →
금융 실행 → 만기·사후관리`에 가깝다. 따라서 TradeFlow도 상품 목록보다 거래 단계와 고객의
의사결정을 중심으로 평가한다.

## 3. 종합 결론

TradeFlow의 현금흐름, 환노출, 자금 공백, K-SURE 후보, 근거와 검토 게이트는 조사된 고객 문제와
방향이 일치한다. 특히 수입 원자재 대금을 먼저 지급하고 완제품 수출대금을 나중에 회수하는
제조기업에는 현재의 연결 거래 분석이 분명한 가치를 제공한다.

다만 현재 서비스는 USD T/T 거래와 환위험 분석에 무게가 있고, 조사에서 확인한 고객의 전체
업무인 생산자금, 수출채권 회수, 수입금융, 지급보증과 사후관리까지 연결하지는 못한다. 그러므로
현재 제품을 `수출입금융 실행 플랫폼`으로 평가하면 범위가 부족하지만, `은행 상담 전 거래구조와
필요 금융을 정리하는 근거 기반 의사결정 워크스페이스`로 정의하면 적합성이 높다.

KB 데이터와 API를 확보하지 못한 현재 단계에서 KB 전용 구현을 만드는 것은 적절하지 않다.
대신 금융기관 중립적인 계약과 수동 인계 경로를 먼저 만들고, 향후 제휴 시 KB 어댑터를 추가할
수 있도록 확장 경계를 유지해야 한다.

## 4. 고객군별 적합성

| 고객군 | 핵심 과업 | 현재 적합성 | 제품 결정 |
|---|---|---:|---|
| 원자재를 수입하고 완제품을 수출하는 제조기업 | 생산·수입대금과 수출대금 회수 사이 공백, 환노출 관리 | 높음 | 초기 핵심 고객 |
| 수출 제조기업 | 선적 전 생산자금과 선적 후 채권 조기 현금화 | 중간 | K-SURE·자금 공백 기능을 확장한 1차 인접 고객 |
| 무역상·외상 수출기업 | 거래처 위험, D/P·D/A·O/A 채권 회수 | 낮음 | 결제방식·거래처 위험 모델 이후 |
| 원자재·부품 수입기업 | 선지급 부담, L/C·Usance·구매금융 | 낮음 | 수입금융 상품 포트가 확보된 뒤 |
| 해외 프로젝트 수행기업 | 입찰·계약이행·선수금환급 등 지급보증 | 낮음 | 보증 수명주기 모델 이후 |
| 글로벌 온라인 셀러 | 소액·다건 정산, 외화계좌와 환전비용 | 낮음 | 정산 데이터 연계가 가능한 별도 트랙 |
| 해외진출기업 | 외국환 신고, 현지법인과 현지금융 | 낮음 | 현재 초기 범위 밖 |

초기 핵심 고객을 수출기업 전체로 넓히기보다 `반복적으로 원자재를 수입하고 제품을 수출하는
중소·중견 제조기업`으로 좁히는 것이 적절하다. 이 고객은 수입과 수출 현금흐름을 함께 보아야
하고 자연헤지, 자금 공백, 선물환과 K-SURE 지원 후보를 한 화면에서 검토할 이유가 가장 크다.

## 5. 현재 구현 평가

### 5.1 고객 문제와 잘 맞는 부분

- 수출 수취와 수입 지급을 하나의 통화별 현금흐름으로 연결한다.
- 결제일 기준 자금 공백과 순환노출을 결정론적으로 계산한다.
- 선물환과 환변동보험을 수치·출처·가용성 상태와 함께 검토한다.
- K-SURE 환변동보험, 단기수출보험과 선적전 수출신용보증 후보 규칙이 있다.
- 누락 정보, 조건 불충족, 출처 만료와 전문가 확인 필요를 서로 다른 상태로 유지한다.
- 신청 필요서류, 다음 행동, 근거와 규칙 버전을 결과에 보존한다.
- 문서 업로드·추출·사용자 확인과 거래·문서 불일치 검토 기반이 있다.

이 기반은 기업이 은행에 방문하기 전에 거래 구조, 현금 공백, 필요한 금융 목적과 준비할 자료를
정리하는 데 유용하다.

### 5.2 고객 조사 이후 더 분명해진 격차

#### 거래 구조의 표현 범위

실제 입력 경로는 USD와 T/T를 기본값으로 고정하고 다른 통화와 결제방식을 거절한다.
도메인 열거형에는 L/C, D/P와 D/A가 있지만 고객 여정에서는 사용할 수 없다. 조사된 대표
고객의 O/A 90일 수출, 선지급 수입, 수입 L/C와 Payment Usance 시나리오를 표현하려면 최소한
다음 정보가 거래 모델과 입력 흐름에 필요하다.

- 결제방식과 사전·사후송금 구분
- 계약일, 선적예정일, 선적일과 결제만기
- 생산·원자재 구매에 필요한 자금 시점
- 수출채권 회수 조건과 결제기간
- 필요한 보증 종류
- 금융 목적과 희망 실행 시점

#### 금융 상담 준비 패킷

현재 결과는 지원 후보와 다음 행동을 제공하지만, 실제 은행 상담에서 확인하는 수출입 실적,
해외 거래처, 결제조건, 자금용도, 필요 한도와 증빙을 하나의 상담 패킷으로 완성하지 않는다.
DecisionPacket을 확장해 다음 내용을 사람이 읽을 수 있고 구조화된 형태로 내보내는 것이 필요하다.

- 기업과 거래 요약
- 현금 공백과 환노출
- 금융 필요 시점과 금액
- 후보 금융 유형과 미확인 조건
- K-SURE 후보와 근거
- 준비된 문서와 누락 문서
- 은행에 확인할 질문
- 사용자가 동의한 전달 범위

#### 검토와 업무 인계

현재 `review_required`는 사람이 확인해야 한다는 사실만 표시한다. 영업점 또는 RM 지정, 상담
요청, 추가자료 요청, 추천서, 보증서·보험증권, 약정과 실행 상태는 관리하지 않는다. 실제 실행을
자동화하지 않더라도 최소한 `수동 상담 준비 완료 → 전달 동의 → 외부 상담 중 → 결과 기록` 정도의
중립적인 인계 상태는 필요하다.

#### 운영 준비도

K-SURE 규칙팩은 독립 도메인 전문가 승인 전이며 `draft`, `production_ready=false` 상태다.
따라서 현재 지원 결과는 구조와 사용자 흐름을 검증하는 후보이지 실제 신청 자격 또는 은행의
취급 가능 판정으로 사용해서는 안 된다.

또한 선적전 수출신용보증 규칙이 요구하는 `financing.has_bank_consultation`은 현재 웹 요청의
거래 사실 허용 목록에 포함되지 않는다. 누락 정보로 표시된 뒤 사용자가 답해도 같은 분석을
정상적으로 다시 실행할 수 있도록 입력 계약을 일치시켜야 한다.

## 6. KB 연계에 대한 제품 원칙

### 6.1 현 단계의 경계

- KB 내부 신용등급, 고객별 금리·한도·담보와 취급 가능 여부를 추정하지 않는다.
- 공개 페이지를 실시간 상품 API처럼 사용하지 않는다.
- KB기업뱅킹, KB스타기업뱅킹 또는 EDI에 제출·주문이 가능한 것처럼 표시하지 않는다.
- `KB 추천`, `승인 가능`, `한도 확정`처럼 금융기관의 판단으로 오인될 표현을 사용하지 않는다.
- KB 연결이 없을 때도 핵심 분석과 상담 준비 패킷이 독립적으로 동작해야 한다.

### 6.2 확장 가능한 모듈 경계

핵심 도메인에는 KB 상품명이나 페이지 ID를 직접 고정하지 않고 다음 금융기관 중립 계약을 둔다.

| 포트 | 책임 | 연계가 없을 때의 동작 |
|---|---|---|
| `BankProductCatalogProvider` | 금융기관별 상품, 대상 거래와 공개 조건 정규화 | 범용 금융유형만 제시 |
| `BankEligibilityEvidenceProvider` | 고객 동의가 있는 등급·한도·상담 결과 증거 수신 | 미확인 상태 유지 |
| `BankConsultationHandoffProvider` | 상담 패킷 전달과 접수 식별자 반환 | 다운로드 또는 수동 전달 |
| `BankApplicationStatusProvider` | 추천·보증·약정·실행 상태 조회 | 사용자가 결과를 직접 기록 |
| `BankChannelProvider` | 영업점·기업뱅킹·EDI 등 허용 채널 안내 | 공식 공개 링크와 연락 경로만 표시 |

구현 상태는 적어도 다음과 같이 구분한다.

- `unavailable`: 데이터나 연계 계약이 없음
- `manual`: 사용자가 상담 패킷을 내려받아 직접 전달
- `configured`: 조직별 연결 정보와 권한이 설정됨
- `live`: 검증된 API·파일·EDI 연결로 실제 송수신 가능

향후 KB 제휴가 확정되면 `integration` 리프에 KB 전용 어댑터와 별도 상품 카탈로그·규칙팩을
추가한다. 핵심 분석, DecisionPacket과 화면은 위 중립 계약만 의존해야 한다.

## 7. 권장 제품 정의

현재 단계의 제품 정의는 다음이 적절하다.

> TradeFlow는 반복적인 수출입 거래가 있는 중소·중견 제조기업이 계약, 생산, 선적과 결제 사이의
> 자금 공백과 환위험을 계산하고, 이용 가능한 금융·보증 후보와 준비자료를 근거와 함께 정리하여
> 금융기관 및 전문가 상담을 준비하도록 돕는 의사결정 워크스페이스다.

현재 단계에서 피해야 할 정의는 다음과 같다.

- KB 수출입금융 실행 플랫폼
- 은행 상품 자동 추천·승인 서비스
- 대출·보증 자동 신청 서비스
- 모든 수출입기업을 위한 종합 무역 플랫폼

## 8. 우선순위

### P0: 초기 고객의 핵심 여정 완성

1. 수입 원자재 지급부터 완제품 수출대금 회수까지 거래 단계와 현금 공백을 표현한다.
2. T/T 외 결제방식을 계산 또는 규칙에 사용하지 못하더라도 정확히 입력·보존하고 지원 범위를
   명시한다.
3. 은행 상담에 필요한 거래·자금·문서·질문을 상담 준비 패킷으로 제공한다.
4. 누락 정보 큐의 모든 입력이 API 계약을 통과하고 재판정으로 이어지게 한다.

### P1: 금융기관 중립 확장 경계

1. 상품 카탈로그, 자격 증거, 상담 인계와 상태 조회 포트를 설계한다.
2. 기본 구현은 `manual` 방식으로 제공한다.
3. 금융기관별 데이터가 없어도 범용 금융 목적과 확인 질문을 제공한다.
4. K-SURE 규칙팩의 독립 전문가 검토와 승격 절차를 완료한다.

### P2: 인접 고객 확장

1. 수출 제조기업의 선적 전·후 금융
2. 원자재 수입기업의 선지급·Usance
3. 무역상의 D/P·D/A·O/A 채권 회수
4. 해외 프로젝트 기업의 지급보증

글로벌 셀러와 해외진출기업은 필요한 데이터와 업무 흐름이 현재 핵심 고객과 크게 다르므로 별도
제품 검증 없이 같은 MVP에 포함하지 않는다.

## 9. 다음 리뷰의 완료 기준

- 초기 핵심 고객과 제외 고객이 제품 비전·사용자 흐름·로드맵에서 일관되게 표현된다.
- 대표 고객 시나리오 한 건이 `계약 → 자금 투입 → 선적 → 대금 회수 → 환위험 → 상담 준비`까지
  끊기지 않고 실행된다.
- 결제방식, 선적일, 결제기간, 금융 목적과 필요 보증을 손실 없이 입력·저장한다.
- 모든 누락 정보 질문이 유효한 API 입력과 재판정으로 연결된다.
- 상담 준비 패킷에 입력, 계산, 후보, 근거, 문서, 누락 정보와 사용자 동의 범위가 포함된다.
- 금융기관 연계가 없는 환경에서 `manual` 상태가 정직하게 표시된다.
- 특정 금융기관 어댑터가 핵심 도메인 변경 없이 추가될 수 있음을 계약 테스트로 검증한다.

준비 완료를 의미하지 않는다.

## 11. 2026-07-31 구현 반영

이 리뷰에서 확인한 P0 단절 중 다음 항목을 구현했다.

- 복합 수출·수입 문장을 두 거래 후보로 분리하고 사용자 확인 전에는 정상 분석을 반환하지 않는다.
- `trade.payment_term_days`, `financing.purpose`,
  `financing.has_bank_consultation` 입력을 거래별 증거로 조립해 재판정한다.
- 로그인된 저장 분석에서 명시적 동의 후 `bank_consultation.v1` 상담 패킷을 생성한다.
- 기본 인계는 `manual_packet`이며 KB 시스템 자동 전송·접수·승인을 주장하지 않는다.
- 패킷 준비 행위는 tenant 감사 로그에 기록하고 원문 문서 콘텐츠는 포함하지 않는다.
- 첫 화면에 현재 자동 계산 범위인 `USD · T/T 송금`을 표시한다.

세부 경계는 [ADR-0028](../adr/0028-bank-neutral-consultation-handoff.md)을 따른다. 실제 KB
접수 API, 한도·금리·신용 판단과 상담 상태 동기화는 제휴 계약과 인터페이스 확보 이후의
integration 작업이다.
