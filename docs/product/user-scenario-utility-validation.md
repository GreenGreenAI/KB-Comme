# 실제 사용자 시나리오 기반 서비스 효용 검증

## 1. 목적

이 문서는 [고객층 조사 기반 서비스 및 KB 연계 준비도 리뷰](customer-and-kb-service-review.md)의
제품 가설을 실제 사용자 시나리오로 검증한다. 기능의 존재보다 고객이 원하는 결정을 끝까지 내릴
수 있는지를 평가한다.

핵심 검증 질문은 다음과 같다.

1. 수출입 제조기업이 자신의 거래를 자연스럽게 설명할 수 있는가?
2. 서비스가 현금 공백과 환위험에 관한 새로운 판단을 제공하는가?
3. 금융지원 후보를 찾고 누락 정보를 보완해 다시 판정할 수 있는가?
4. 분석 결과를 실제 금융기관 상담 준비로 연결할 수 있는가?

## 2. 검증 대상 고객과 상황

### 고객

- 국내 중소 제조기업
- 베트남에서 원자재를 수입하고 미국으로 완제품을 수출
- 전담 외환·무역금융 인력이 없음

### 거래

| 거래 | 금액 | 예정일 | 결제방식 |
|---|---:|---:|---|
| 원자재 수입대금 지급 | USD 60,000 | 2026-08-25 | T/T |
| 완제품 수출대금 수취 | USD 100,000 | 2026-10-24 | T/T |

### 고객이 알고 싶은 것

- 수출대금으로 수입대금을 충당할 수 있는가?
- 중간에 필요한 운전자금은 얼마인가?
- 실제 환노출은 얼마인가?
- 선적 전 생산자금 또는 K-SURE 지원을 검토할 수 있는가?
- 은행에 어떤 자료와 질문을 가져가야 하는가?

## 3. 성공 기준

| 단계 | 성공 기준 |
|---|---|
| 거래 입력 | 한 번의 자연스러운 설명에서 두 거래를 모두 인식하거나, 분리 입력이 필요함을 명확히 안내 |
| 현금흐름 | 날짜순 유입·유출과 최대 자금 공백을 정확히 계산 |
| 자연헤지 | 경제적 상계와 결제시점에 실제 사용할 수 있는 상계를 구분 |
| 환위험 | 노출 방향에 맞는 불리한 환율과 현금흐름 영향을 표시 |
| 지원제도 | 고객·거래 사실을 보완하면 후보 판정이 실제로 갱신 |
| 실행 연결 | 금융기관 상담에 필요한 요약, 증빙과 확인 질문 제공 |
| 안전성 | 미확인 자격, 상품 가용성과 금융기관 승인을 확정적으로 표현하지 않음 |

## 4. 실행 결과

### 시나리오 A: 복합 거래를 한 문장으로 입력

입력:

> 베트남에서 원자재 6만 달러를 수입해 8월 25일에 지급하고, 완제품을 미국에
> 10만 달러 수출해 10월 24일에 받습니다. 생산자금과 환위험을 같이 검토하고 싶어요.

실제 결과:

- 수입 USD 60,000 한 건만 인식했다.
- 수출 USD 100,000과 10월 24일 수취는 거래로 생성되지 않았다.
- 순노출 `-60,000 USD`, 자금 공백 `60,000 USD`, 자연헤지 `0 USD`를 반환했다.
- 지원제도 워커는 실행되지 않았다.

판정: **실패**

이 입력은 핵심 고객이 가장 자연스럽게 설명할 수 있는 방식이다. 일부 거래만 인식한 상태에서
정상 분석 결과를 반환하면 사용자는 두 거래가 모두 반영됐다고 오해할 수 있다. 복합 거래를
지원하기 전까지는 문장에서 둘 이상의 거래 징후를 발견하면 분석을 중단하고 거래별 분리 확인을
요청해야 한다.

### 시나리오 B: 같은 거래를 두 건으로 구조화해 입력

실제 결과:

| 결과 | 값 |
|---|---:|
| 총 경제적 자연헤지 | USD 60,000 |
| 결제시점이 맞는 상계 | USD 0 |
| 최종 순노출 | 수출 USD 40,000 |
| 최대 자금 공백 | USD 60,000 |
| 자금 공백 발생일 | 2026-08-25 |

시장 시나리오는 수출 순노출 USD 40,000에 대해 불리한 환율을 `1,362.67 KRW/USD`,
현금흐름 감소액을 `KRW 4,145,200`으로 계산했다.

판정: **핵심 효용 통과**

단순히 수출 USD 100,000과 수입 USD 60,000을 빼면 USD 40,000만 남는다고 생각하기 쉽다.
TradeFlow는 수입대금이 먼저 지급되기 때문에 USD 60,000의 자금 공백이 실제로 발생하고,
전체 기간의 자연헤지와 결제시점에 사용 가능한 상계가 다르다는 점을 보여준다.

이는 다음 실제 행동으로 연결할 수 있는 유효한 정보다.

- 8월 25일 이전 USD 60,000 운전자금 또는 수입금융 상담
- 수출 순노출 USD 40,000에 대한 환위험 검토
- 수출대금 회수일 단축 또는 수입대금 지급일 연장 협상
- 은행 상담 시 두 거래의 만기 불일치를 명시

### 시나리오 C: 선적 전 생산자금과 K-SURE 후보 탐색

입력 조건:

- 국내 중소기업 자기선언
- 신용 제한 사유 없음 자기선언
- K-SURE 수출자 등급 B 자기선언
- 수출 USD 100,000
- 선적 전 무역금융 목적
- 결제기간 90일

실제 결과:

- K-SURE 환변동보험 후보는 `expert_confirmation_required`로 표시됐다.
- 공식 확인이 필요한 자기선언을 자동 자격으로 승격하지 않았다.
- 필요서류 세트와 K-SURE 상담·신청 행동을 반환했다.
- 단기수출보험과 선적전 수출신용보증은 계속 `insufficient_information`으로 남았다.
- 요청에 포함한 `trade.payment_term_days`와 `financing.purpose`가 판정 사실로 연결되지 않았다.
- 은행 상담 여부는 누락 정보로 표시됐지만 현재 거래 사실 API가 해당 필드 입력을 허용하지 않는다.

판정: **부분 통과**

후보, 근거, 필요서류와 전문가 확인 경계는 실질적인 상담 준비 가치가 있다. 그러나 사용자가
누락 정보를 제공해도 규칙 입력 증거로 조립되지 않거나 API에서 거절되므로 후보 탐색을 끝까지
완료할 수 없다. 현재는 “무엇을 더 알아야 하는지 보여주는 기능”까지 유용하며, “답을 보완해
판정을 좁히는 기능”은 미완성이다.

### 시나리오 D: 수입신용장 고객

입력:

- 수입 USD 60,000
- 결제방식 L/C

실제 결과:

- `지금은 T/T 송금 방식만 분석할 수 있습니다`라는 입력 문제를 반환했다.

판정: **정직한 범위 제한, 고객 과업은 실패**

지원하지 않는 결제방식을 T/T로 바꾸어 계산하지 않는 점은 안전하다. 다만 고객 조사에서
수입신용장은 핵심 수입금융 업무이므로, 서비스가 전체 수출입금융을 지원한다고 표현해서는 안 된다.

### 시나리오 E: 금융기관 상담으로 전환

검토 결과:

- `review_required`, 다음 행동, 담당 기관과 필요서류는 제공한다.
- 금융기관 상담용 단일 요약 패킷, 전달 동의, 다운로드와 수동 인계 상태는 없다.
- 영업점·RM 접수, 추가자료 요청과 상담 결과를 기록하는 흐름이 없다.
- KB 데이터와 API가 없으므로 실제 제출이나 상태 조회는 지원하지 않는다.

판정: **실패**

외부 API 부재는 현재 단계의 결함이 아니다. 그러나 API 없이도 가능한 상담 패킷 다운로드와
수동 인계 상태가 없기 때문에 분석이 고객의 다음 업무로 이어지지 않는다.

## 5. 효용 평가

### 5.1 최종 판정

> TradeFlow에는 실질적인 효용이 있다. 다만 그 효용은 현재 “수출입금융 실행”이 아니라
> “수출입 거래의 만기 불일치, 자금 공백과 환노출을 발견하고 상담을 준비하는 것”에 한정된다.

핵심 계산은 스프레드시트로도 가능하지만, TradeFlow는 다음을 한 결과 안에서 결합한다.

- 수출·수입 거래의 날짜순 현금흐름
- 경제적 자연헤지와 실제 만기상계의 구분
- 자금 공백과 환위험의 동시 표시
- 지원 후보의 근거·누락 정보·전문가 검토 상태
- 필요서류와 다음 행동

이 결합은 전담 무역금융 인력이 없는 기업에 의미가 있다. 특히 “전체로는 흑자이지만 수입대금
지급일에는 현금이 없다”는 문제를 발견하는 것은 금융 상담 시점과 필요 한도를 결정하는 직접적인
효용이다.

### 5.2 현재 제공 가능한 약속

현재 사용해도 되는 제품 약속:

> 수출입 지급·수취 일정을 입력하면 통화별 자금 공백과 환노출을 계산하고, 확인 가능한
> 금융지원 후보와 은행 상담 준비사항을 근거와 함께 보여드립니다.

현재 사용하면 안 되는 제품 약속:

- 맞춤 대출상품을 추천한다.
- KB 수출입금융 신청을 연결한다.
- K-SURE 또는 은행의 승인 가능성을 판정한다.
- 모든 결제방식과 수출입 업무를 지원한다.

## 6. 치명도별 발견사항

### P0: 복합 거래 일부 인식 후 정상 분석

한 문장에 두 거래가 있어도 한 건만 인식하고 정상 결과를 반환한다. 잘못된 분석을 신뢰하게 만들
수 있으므로 가장 먼저 막아야 한다.

완료 기준:

- 복수 거래를 각각 생성하거나,
- 둘 이상의 거래 징후를 감지하면 분석하지 않고 분리 확인 질문을 한다.
- 최종 결과 전에 인식한 거래 수·방향·금액·날짜를 사용자가 확인할 수 있다.

구현 상태(2026-07-31): 완료. 혼합 방향 문장은 `needs_trade_split`으로 차단되고 두 후보를
확인한 뒤에만 구조화된 두 거래로 분석한다.

### P0: 누락 정보 보완과 재판정의 단절

`financing.purpose`, `trade.payment_term_days`, `financing.has_bank_consultation` 등 화면과
규칙이 요구하는 사실이 유효한 증거와 함께 다시 판정으로 연결되지 않는다.

완료 기준:

- 질문 가능한 모든 필드가 API 계약에서 허용된다.
- 사용자 답변 또는 외부 증거의 역할을 구분해 FactAssembler에 전달한다.
- 답변 후 해당 `missing_fields`가 사라지거나 다른 명시적 상태로 바뀐다.

구현 상태(2026-07-31): 완료. 세 필드를 거래별 사용자 거래 증거 또는 절차 증거로 분리해
조립하고 재판정한다.

### P1: 상담 준비 산출물 부재

계산 결과가 유용해도 사용자가 금융기관 상담으로 가져갈 수 있는 하나의 결과물이 없다.

완료 기준:

- 거래, 현금 공백, 환노출, 후보, 근거, 문서, 누락 정보와 질문을 한 패킷으로 제공한다.
- 외부 연계가 없을 때 `manual` 인계임을 표시한다.
- 다운로드 또는 공유 전 사용자 동의 범위를 확인한다.

구현 상태(2026-07-31): 수동 인계 MVP 완료. 로그인된 저장 분석과 명시적 동의를 요구하며,
`bank_consultation.v1` JSON을 내려받고 자동 전송은 수행하지 않는다.

### P1: 지원 범위보다 넓은 첫인상

고객 조사 범위는 L/C, D/P, D/A, O/A, 지급보증과 Usance까지 포함하지만 실제 계산 입력은
USD T/T에 한정된다.

완료 기준:

- 진입 화면에서 지원 통화·결제방식을 명확히 표시한다.
- 지원하지 않는 거래도 입력·보존한 뒤 어떤 분석을 할 수 없는지 설명한다.
- 제품 명칭과 소개가 현재 처리 범위를 넘지 않는다.

구현 상태(2026-07-31): 진입 화면 범위 표시는 완료했다. 미지원 거래의 장기 저장과 후속
은행 업무 흐름은 다음 단계다.

### P2: 결과 우선순위

지원·신고·헤지에 필요한 질문이 동시에 많이 나타나면 고객이 당장 필요한 운전자금 판단보다
규정 입력에 먼저 노출될 수 있다.

완료 기준:

- 사용자의 질문과 가장 가까운 과업을 먼저 완료한다.
- 핵심 고객 시나리오에서는 `자금 공백 → 금융 목적 → 상담 준비` 순서를 우선한다.
- 관계없는 신고 구조 질문은 접거나 별도 검토로 미룬다.

## 7. 권장 다음 검증

### 테스트 1: 복합 거래 확인

- 한 문장에 수출·수입 거래 두 건 입력
- 두 건 인식 또는 분리 질문 확인
- 사용자가 거래 요약을 확인한 뒤 계산

### 테스트 2: 누락 정보 폐쇄

- 선적전 수출신용보증 후보 시작
- 기업규모, 금융 목적, 은행 상담 여부를 순서대로 답변
- 같은 후보의 상태가 `insufficient_information`에서 구조적으로 변경되는지 확인

### 테스트 3: 상담 준비 패킷

- 대표 거래 두 건과 지원 후보 생성
- 상담 패킷 출력
- 제3자가 패킷만 보고 필요한 자금, 시점, 미확인 조건과 질문을 설명할 수 있는지 평가

### 테스트 4: 실제 사용자 관찰

초기 고객 조건에 가까운 사용자 5명에게 다음 과업을 제공한다.

> 다음 두 달간 예정된 수출입 거래를 입력하고, 자금이 부족한 시점과 은행에 물어볼 내용을
> 찾아보세요.

관찰 지표:

- 첫 유효 결과까지 걸린 시간
- 거래 인식 수정 횟수
- 자금 공백을 정확히 설명한 사용자 비율
- 다음 행동을 스스로 선택한 사용자 비율
- 상담 패킷을 실제로 사용하겠다는 사용자 비율
- 결과를 신뢰하지 못한 이유

## 8. 검증 환경과 한계

- 기준일: 2026-07-30
- 최신 저장소 코드로 프런트엔드를 빌드하고 FastAPI 분석 API를 실행했다.
- 자연어 입력은 브라우저와 API에서, 구조화된 거래와 규칙 입력은 API에서 재현했다.
- KB 내부 데이터, 고객별 은행 조건과 실제 RM 심사는 검증 범위가 아니다.
- K-SURE 규칙팩은 독립 도메인 전문가 승인 전이므로 운영 자격 판정으로 평가하지 않았다.
- 이 검증은 제품 내부 시나리오 검증이며 실제 고객 인터뷰나 현장 사용성 테스트를 대체하지 않는다.
