# TradeFlow MVP 아키텍처 설계

> 문서 상태: MVP Implementation Spec v1.0
> 상위 문서: TradeFlow 통합 수출입 금융 플랫폼 기획서 (Product/Architecture Draft v0.1)
> 범위: 대회 제출용 프로토타입

---

## 1. 이 문서의 위치

상위 기획서는 제품의 완성형을 정의한다. 이 문서는 그중 **프로토타입 기간에 실제로 만들 것만** 남기고, 상위 문서에 없던 **에이전트 계층과 결정론 도구의 수학 모델**을 추가로 정의한다.

상위 문서와 충돌하는 경우 이 문서가 우선한다. 다만 설계 원칙(§4)과 응답 계약(§13.3)은 상위 문서를 그대로 승계한다.

### 1.1 설계 규율

이 문서 전체를 관통하는 단 하나의 규칙.

> **도구가 없는 에이전트는 만들지 않는다.**

에이전트를 먼저 정의하고 근거를 나중에 붙이면, 근거가 없는 자리를 LLM이 서술로 채운다. 금융 도메인에서 이는 제품 실패다. 따라서 모든 워커 에이전트는 짝이 되는 결정론적 도구를 반드시 가지며, 도구가 준비되지 않은 에이전트는 MVP에서 제외한다.

에이전트의 책임은 셋으로 제한한다.

1. 도구에 넘길 파라미터를 고른다
2. 도구의 결과를 해석한다
3. 입력이 불충분하면 추정하지 않고 멈춘다

**숫자를 생성하는 일은 에이전트의 책임이 아니다.**

## 2. MVP 경계

### 2.1 포함

| # | 항목 | 근거 |
|---|---|---|
| 1 | 기업 프로필 (규모, 업종, 기준통화) | 자격 판정 입력 |
| 2 | 수출·수입 Case 및 TradeProgram 연결 | 자연헤지 계산의 전제 |
| 3 | T/T 결제 거래 | 결제방식 중 가장 단순, 비중 최다 |
| 4 | 외화 Cashflow·자금공백·순환노출 계산 | 제품의 심장 |
| 5 | 환율 스냅샷 수집 및 변동성 추정 | 손익 시뮬레이션의 전제 |
| 6 | 환율 시나리오 밴드 및 손익분기 산출 | 인식 전환의 핵심 출력 |
| 7 | 최적 헤지비율 산출 및 수단 비교 | 처방 단계 |
| 8 | 무역보험·정책자금 후보 자격 판정 | 정보 격차 해소 |
| 9 | 외국환거래 신고의무 사전 경고 | 차별화 요소, 구현 난이도 낮음 |
| 10 | 근거 레코드 및 최신성 검증 | 신뢰성 확보 |
| 11 | 필요서류·다음 행동·상담 질문 생성 | 실행 연결 |
| 12 | `review_required` 플래그 및 사유 표시 | 사람의 최종 통제 원칙 유지 |

| 상위 문서 항목 | 처리 | 이유 |

```text

예외: INFORMATION_INSUFFICIENT
```

T/T 단일 결제방식에서는 이 이상의 상태가 의미를 갖지 않는다.

### 2.4 확정된 미결정 사항

상위 문서 §25의 항목 중 MVP 설계에 필요한 것을 확정한다.

| # | 항목 | 확정 | 근거 |
|---|---|---|---|

## 3. 아키텍처 개요

상위 문서 §9.2의 4계층 구조에 **Agent Layer**를 추가하고, 기존 Decision Layer의 성격을 **결정론 도구 계층**으로 명시한다.

```text
┌─────────────────────────────────────────────┐
│ Channel        기업 Web (단일 화면)          │
├─────────────────────────────────────────────┤
│ Agent Layer    인테이크 · 오케스트레이터      │
│                워커 5 · 근거검증 · 합성        │
├─────────────────────────────────────────────┤
│ Tool Layer     결정론적 계산 엔진·룰 엔진      │
│ (결정론)        LLM 개입 없음                 │
├─────────────────────────────────────────────┤
│ Data           스냅샷 · 근거 스토어 · 도메인DB │
├─────────────────────────────────────────────┤
│ Integration    ECOS · 기업마당                │
└─────────────────────────────────────────────┘
```

**Agent Layer와 Tool Layer의 경계가 이 아키텍처의 핵심이다.** 상위 문서 §4.3(계산과 언어 생성의 분리)이 원칙 선언에 머물러 있었다면, 이 경계가 그것을 구조로 구현한다.

## 4. Agent Layer

### 4.1 런타임 파이프라인

```text
사용자 입력
    │
    ▼
[1] 인테이크              결측 슬롯 확인 · 되묻기 루프
    │
    ▼
[2] 오케스트레이터         호출 계획 수립 · 병렬 그룹 결정
    │
    ├──────┬──────┬──────┬──────┐
    ▼      ▼      ▼      ▼      ▼
   [3]    [4]    [5]    [6]    [7]
  노출    시장   헤지   지원   규제
  산출   시나리오 전략   제도   준수
    │      │      │      │      │
    └──────┴──────┴──────┴──────┘
                 │
                 ▼
        [8] 근거 검증        출처·최신성·재현성
                 │
                 ▼
        [9] 응답 합성        구조화 JSON
                 │
                 ▼
              사용자
```

**의존 관계에 따른 실행 순서**

- 1단계 (병렬): 노출 산출, 시장 시나리오, 지원제도 매칭, 규제 준수
- 2단계: 헤지 전략 (노출 산출 + 시장 시나리오 결과를 입력으로 요구)
- 3단계: 근거 검증 → 응답 합성

### 4.2 에이전트 명세

#### [1] 인테이크 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 자연어·폼 입력을 `TradeCase` 슬롯으로 정규화, 결측 식별 |
| 입력 | 사용자 발화, 폼 값, 기존 세션 상태 |
| 출력 | `TradeCase[]`, `CompanyProfile`, `missing_slots[]` |
| 도구 | 슬롯 스키마 검증기 (필수/선택/형식) |
| 중단 조건 | 필수 슬롯 미충족 시 파이프라인 진행 없이 되묻기 |

**필수 슬롯** (상위 문서 §10.2 기반, MVP 축소)

```json
{
  "direction": "EXPORT | IMPORT",
  "currency": "USD",
  "amount": 100000,
  "expected_payment_date": "YYYY-MM-DD",
  "payment_method": "TT"
}
```

**선택 슬롯**: `country`, `counterparty_id`, `expected_shipment_date`, `advance_payment_ratio`, `contract_date`

**되묻기 정책**: 한 번에 최대 3개. 우선순위는 `amount` → `expected_payment_date` → `direction`. 이 세 개만 있으면 노출 산출이 가능하므로, 나머지는 결과를 보여준 뒤 보강을 유도한다.

> 이 에이전트가 서비스에서 가장 자주 발동된다. 대상 사용자는 자신의 환노출액을 인지하지 못하는 집단이므로, 대부분의 세션이 불완전한 입력으로 시작한다.

#### [2] 오케스트레이터

| 항목 | 내용 |
|---|---|
| 책임 | 어떤 워커를 어떤 순서·병렬로 호출할지 결정 |
| 입력 | 정규화된 `TradeCase[]`, `CompanyProfile`, 사용자 의도 |
| 출력 | `execution_plan` (워커 목록, 실행 단계, 각 워커 파라미터) |
| 도구 | 없음 (판단 전용) |
| 중단 조건 | 호출 가능한 워커가 0개일 때 |

**MVP 라우팅 규칙**

| 조건 | 호출 워커 |
|---|---|
| 항상 | 노출 산출, 시장 시나리오 |
| 순노출 ≠ 0 | 헤지 전략 |
| 기업 프로필 존재 | 지원제도 매칭 |
| 거래 구조에 상계·선수금·기간초과 요소 | 규제 준수 |

판정은 구현 단계와 관계없이 결정론 규칙·도구가 담당한다. 워커가 모두 연결된 뒤에도
LLM은 호출 경로 선택과 `DecisionPacket` 설명만 담당하며 판정 자체로 전환하지 않는다.

#### [3] 노출 산출 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 통화·시점별 순노출과 자금공백 산출 |
| 입력 | `TradeCase[]`, 보유 외화 잔액 |
| 출력 | `CashflowEvent[]`, `ExposurePosition[]`, `funding_gap[]` |
| 도구 | **Cashflow·Exposure Engine** (§5.1) |
| 중단 조건 | 금액 또는 결제일 결측 |

#### [4] 시장 시나리오 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 결제 시점까지의 환율 분포 밴드 생성 |
| 입력 | 통화쌍, 잔여 기간(영업일), 신뢰수준 |
| 출력 | `volatility`, `scenario_band`, `quantiles` |
| 도구 | **Volatility·Scenario Generator** (§5.2) |
| 중단 조건 | 환율 스냅샷 최신성 위반(`STALE`) |

에이전트의 판단 영역은 관측 기간(기본 60영업일)과 신뢰수준(기본 90%) 선택에 한정한다. 변동성 추정과 밴드 산출은 전적으로 도구가 수행한다.

#### [5] 헤지 전략 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 목표 손실한도를 만족하는 헤지비율 산출, 이용 가능 수단 필터링 |
| 입력 | 순노출, 시나리오 밴드, 담보·신용 여력, 목표 손실한도 |
| 출력 | `optimal_ratio`, `instrument_candidates[]`, `payoff_comparison` |
| 도구 | **Hedge Ratio Optimizer** (§5.3) |
| 중단 조건 | h=1로도 목표 미달 시 → `HEDGE_INSUFFICIENT` 반환 |

**수단 필터링 규칙** (담보·신용 제약 반영)

| 수단 | 이용 조건 |
|---|---|
| 은행 선물환 | 신용라인 또는 담보 보유 |
| K-SURE 환변동보험 | 담보·증거금 불요. 중소기업 보험료 할인 적용 |
| 자연헤지 | 반대방향 동일통화 현금흐름 존재 |
| 결제조건 조정 | 계약 협상 여지 존재 |

담보·신용 여력이 없다고 응답한 기업에게 선물환을 제시하지 않는다. 이 필터가 없으면 "쓸 수 없는 상품 추천"이 되어 서비스 신뢰가 무너진다.

#### [6] 지원제도 매칭 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 무역보험·정책자금 후보 탐색 및 자격 판정 |
| 입력 | `CompanyProfile`, `TradeCase[]` |
| 출력 | `support_candidates[]`, `excluded_candidates[]`, `missing_information[]` |
| 도구 | **Eligibility Rule Engine** (§5.4) |
| 중단 조건 | 기업 프로필 결측 |

판정 상태는 상위 문서 §11.5를 그대로 승계한다.
`ELIGIBLE_CANDIDATE` / `CONDITIONALLY_ELIGIBLE` / `NOT_ELIGIBLE` / `INSUFFICIENT_INFORMATION` / `EXPERT_CONFIRMATION_REQUIRED` / `SOURCE_EXPIRED`

**제외 사유를 반드시 반환한다.** 후보 목록만 주는 서비스는 검색기지만, "왜 이건 안 되는지"를 주는 서비스는 자문이다.

#### [7] 규제 준수 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 외국환거래법상 신고의무 발생 여부 판정 |
| 입력 | 거래 구조 (상계 여부, 선수금 비율, 결제 기간, 금액) |
| 출력 | `filing_obligations[]`, `warnings[]` |
| 도구 | **FX Regulation Rule Engine** (§5.5) |
| 중단 조건 | 거래 구조 정보 결측 시 판정 보류 |

완전 결정론 워커다. LLM의 역할은 사용자 입력을 룰 엔진 입력 형식으로 정규화하는 것뿐이며, 판정 자체에는 개입하지 않는다.

#### [8] 근거 검증 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 모든 판단의 출처·최신성·재현성 확인, `review_required` 결정 |
| 입력 | 워커 출력 전체 |
| 출력 | `evidence[]`, `review_required`, `review_reasons[]` |
| 도구 | **Evidence Validator** (상위 문서 §11.8 승계) |

**`review_required = true` 트리거**

- 거래 금액이 임계치 초과
- 판단 근거의 `effective_to` 경과 또는 최신성 SLA 위반
- 서로 다른 공식 출처 간 조건 충돌
- `EXPERT_CONFIRMATION_REQUIRED` 판정 포함
- `HEDGE_INSUFFICIENT` 반환

#### [9] 응답 합성 에이전트

| 항목 | 내용 |
|---|---|
| 책임 | 워커 출력을 단일 응답으로 통합, 사용자 수준 설명 생성 |
| 입력 | 워커 출력 전체 + 근거 검증 결과 |
| 출력 | 상위 문서 §13.3 응답 계약 JSON |
| 도구 | 없음 (서술 전용) |

**엄격 규칙**: 도구가 산출한 수치를 그대로 인용한다. 재계산·반올림·근사 표현을 금지한다. 수치의 단위·기준환율·기준시점을 함께 표기한다.

## 5. Tool Layer — 결정론 도구

### 5.1 Cashflow·Exposure Engine

**순노출**

```text
통화 c, 시점 t에 대하여
  E(c, t) = Σ(수취 예정액) - Σ(지급 예정액) + 보유잔액
```

**자금공백**

```text
G(t) = min( 0, 누적잔액(t) )
누적잔액(t) = 보유잔액 + Σ_{τ≤t} CashflowEvent(τ)
```

**자연헤지 가능액**

```text
H_nat = min( Σ수취, Σ지급 )   [동일 통화·중첩 기간]
잔여노출 = |Σ수취 - Σ지급|
```

**검증**: 상위 문서 §5.2 기준 시나리오(수입 USD 60,000 / 30일, 수출 USD 100,000 / 90일, 보유 USD 20,000)에 대해 30일 시점 자금공백 USD -40,000, 자연헤지 USD 60,000, 잔여노출 USD 40,000이 산출되어야 한다.

### 5.2 Volatility·Scenario Generator

```text
일별 로그수익률   r_t = ln(S_t / S_{t-1})
실현변동성        σ_d = stdev(r_t),  최근 N영업일 (기본 N=60)
기간 스케일링     σ_T = σ_d × √T     (T = 결제일까지 영업일수)
분위수 밴드       S_band = S_0 × exp(±z × σ_T)
                  z = 1.645 → 90%,  z = 1.96 → 95%
```

**드리프트 항은 0으로 고정한다.** 이는 상위 문서 §3.2("미래 환율의 방향이나 가격을 확정적으로 예측하지 않는다")를 수학적으로 구현한 것이다. 드리프트를 도입하는 순간 제품 원칙과 자기모순이 발생한다.

**검증 — 백테스트 커버리지**

과거 각 시점 t에서 생성한 90% 밴드가 실제 t+T 시점 환율을 포함한 비율을 측정한다. 목표 범위는 85~95%. 이 지표는 "환율을 예측하지 않는다"는 주장의 정량적 근거가 된다.

### 5.3 Hedge Ratio Optimizer

```text
변수
  h  = 헤지비율, 0 ≤ h ≤ 1
  E  = 순노출액
  S_0 = 현재 환율
  F  = 선물환율 또는 보장환율
  c  = 헤지비용률
  π_0 = 헤지 전 기준 영업이익

헤지 후 영업이익
  π(S, h) = π_0 + E·[ (1-h)(S - S_0) + h(F - S_0) ] - c·h·E·S_0

목표
  P( π < π_floor ) ≤ α 를 만족하는 최소 h

풀이
  S_α = S_0 · exp( -z_α · σ_T )   (불리한 방향 α-분위수)
  위 식에 대입하면 h에 대해 선형 → 닫힌 해 존재
```

**하드 제약 h ≤ 1**. 실노출을 초과하는 헤지는 위험 축소가 아니라 신규 투기 포지션이며, 코드 레벨에서 차단한다.

**h = 1로도 목표를 달성할 수 없는 경우**, 임의의 값을 반환하지 않고 `HEDGE_INSUFFICIENT`와 함께 대안(판가 전가, 결제조건 조정, 목표 재설정)을 반환한다. 상위 문서 §4.5 불확실성 명시 원칙에 해당한다.

**검증 — 손익분포 3종 비교**

h=0 / h=h\* / h=1 각각의 손익분포를 나란히 출력한다. 이로써 결과가 "추천"이 아니라 "비교 제시"가 되며, 상위 문서 §21의 권유 표현 금지 요건을 충족한다.

**부속 산식 — 손익분기 환율과 적자 전환 확률**

```text
S_be  = S_0 - π_0 / E
P(π<0) = Φ( ln(S_be / S_0) / σ_T )
```

### 5.4 Eligibility Rule Engine

상위 문서 §11.5의 규칙 표현을 승계한다.

규칙은 상품별 공식 임계값을 사용한다. 예를 들어 단기수출보험(선적후·개별)의
결제기간은 현재 공식 안내상 2년 이내이며, 포괄보험은 180일 이내다. 공통 예시값을
여러 상품에 재사용하지 않는다.

**MVP 대상 제도**

| 제도 | 판정 축 |
|---|---|
| K-SURE 환변동보험 | 기업규모, 거래방향, 헤지기간, 품목 |
| K-SURE 단기수출보험 | 기업규모, 결제기간, 수입자 소재국 |
| 수출신용보증(선적전) | 기업규모, 무역금융 이용 여부 |
| 기업마당 수집 지원사업 | 공고별 조건 파싱 결과 |

**출력 3종 필수**: 포함 사유, 제외 사유, 누락 정보. 세 개가 모두 있어야 자문으로 성립한다.

### 5.5 FX Regulation Rule Engine

완전 결정론 룰 엔진. 판정 결과에 확률이나 정도 표현을 사용하지 않는다.

| 조건 | 판정 |
|---|---|
| 일방 금액 USD 5,000 이하 상계 | 다른 예외·사실관계 확인 후 신고예외 후보 |
| USD 5,000 초과 양자간 상계 | 외국환은행 보고 검토 대상 |
| USD 5,000 초과 다자간 상계 또는 상계센터 경유 | 한국은행 신고 검토 대상 |
| 제3자 지급·수령 금액 USD 5,000 초과 USD 10,000 이하 | 외국환은행 신고 검토 대상 |
| 제3자 지급·수령 금액 USD 10,000 초과 | 한국은행 신고 검토 대상 |
| 외국환은행을 통하지 않는 지급이며 제5-11조 예외·타기관 확인 대상이 아님 | 한국은행 신고 검토 대상 |
| 건당 USD 100,000 초과 수출대금을 선적 전 1년 초과하여 수령 | 예외품목 확인 후 한국은행 신고 검토 대상 |
| 건당 USD 100,000 초과 수입대금을 서류·물품 수령 전 1년 초과하여 지급 | 예외품목 확인 후 한국은행 신고 검토 대상 |

현재 규칙은 [국가법령정보센터 외국환거래규정](https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000281984&chrClsCd=010201)과
[한국은행 외환거래별 신고 안내](https://www.bok.or.kr/portal/main/contents.do?menuNo=200399)를
함께 근거로 사용한다. 공개 안내만으로 확정할 수 없는 예외·사실관계는
`INSUFFICIENT_INFORMATION` 또는 `EXPERT_CONFIRMATION_REQUIRED`를 반환한다.
예외 입력은 포괄 boolean이 아니라 `knowledge/exception_catalogs/`의 조문 번호
기반 enum을 사용한다. `none`은 전체 예외와 증빙을 대조한 경우에만 허용하며
LLM은 enum을 추정하거나 신고 후보를 면제할 수 없다.

### 5.6 (P2) Country Risk Scorecard

MVP 필수는 아니나 도구 명세만 확정해 둔다.

```text
지표 x_i → 정규화 z_i (백분위 또는 표준화)
Score = Σ w_i · z_i ,  Σ w_i = 1
등급 = 스코어 구간 매핑 (A~E)
```

가중치 `w_i`는 버전 관리 대상이며, 출력에 `w_i × z_i` 기여도 분해를 반드시 포함한다. 등급만 반환하면 블랙박스가 된다.

## 8. 구현 순서

### Sprint 1 — 수직 관통

인테이크 → 노출 산출 → 합성만 연결하여 기준 시나리오를 끝까지 통과시킨다. 오케스트레이터는 고정 호출로 둔다.

**완료 조건**: 기준 시나리오 입력 시 자금공백·자연헤지·잔여노출이 §5.1 검증값과 일치하고, 사람이 읽을 수 있는 요약이 출력된다.

### Sprint 2 — 시장 시나리오와 헤지

시장 시나리오 워커와 헤지 전략 워커를 추가한다. 백테스트 커버리지를 측정한다.

**완료 조건**: 손익분기 환율과 적자 전환 확률이 출력되고, h=0/h\*/1 손익분포 비교가 표시된다. 백테스트 커버리지가 85~95% 범위에 든다.

### Sprint 3 — 오케스트레이터 활성화

지원제도 매칭과 규제 준수 워커를 추가하고, 오케스트레이터의 판단 로직을 켠다. 병렬 실행을 구현한다.

**완료 조건**: 워커 5개가 조건에 따라 선택 호출되며, 실패한 워커가 있어도 나머지 결과로 응답이 생성된다.

### Sprint 4 — 근거와 검토

근거 검증 워커를 붙이고 `review_required` 배지를 화면에 노출한다.

**완료 조건**: 모든 판단에 출처와 기준일이 표시되고, 근거 부족 항목이 상담 필요로 분류된다.

## 9. 수용 기준

상위 문서 §20을 MVP 범위로 축소한다.

### 9.1 계산

- 동일 입력은 동일 결과를 반환한다
- 기준 시나리오의 자금공백·자연헤지·잔여노출이 정답 산식과 일치한다
- 통화, 기준환율, 단위, 반올림 방식이 결과에 표시된다
- 과거 스냅샷으로 동일 결과를 재현할 수 있다
- 헤지비율이 항상 0 이상 1 이하다
- 백테스트 커버리지가 목표 범위 내에 있다

### 9.2 근거

- 모든 추천 후보가 공식 출처와 기준일을 가진다
- 만료된 출처는 판단 근거로 사용되지 않는다
- 공식 데이터가 없으면 추정하지 않고 정보 부족으로 처리한다

### 9.3 에이전트

- 필수 슬롯 결측 시 파이프라인이 진행되지 않고 되묻는다
- 워커 하나가 실패해도 나머지 결과로 응답이 생성된다
- 합성 결과의 모든 수치가 도구 출력과 일치한다
